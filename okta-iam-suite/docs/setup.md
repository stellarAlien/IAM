# Configure a real Okta Integrator Free Plan org

This is administrator setup, not an automated takeover of your tenant. Keep the suite in a dedicated test org and never assign its users/groups to production applications. No signup, administrator consent, MFA enrollment, API token or app credential can be generated by repository code without access to your org.

## 1. Create the current free org

Use [Okta developer signup](https://developer.okta.com/signup/) → **Workforce Identity → Integrator Free Plan**. Use an eligible unique business email, activate the administrator, and enroll strong MFA. Keep a recovery/break-glass administrator separate from the actors; do not use any actor as the org's only administrator.

Record the org's non-admin origin, such as `https://integrator-123456.okta.com`. Do **not** use the `-admin` hostname. The suite supports standard Okta domains (`okta.com`, `oktapreview.com`, `okta-emea.com`), not arbitrary custom domains. No trial org or paid feature is required for the implemented tracks. Check **Directory → People** and the current user cap before activating actors.

## 2. Create an OIDC public Native application

Admin Console → **Applications → Applications → Create App Integration**:

- Sign-in method: **OIDC – OpenID Connect**.
- Application type: **Native Application**, not SPA, Web or SAML.
- Name: `IAM Lab PKCE`.
- Grant type: **Authorization Code**. Disable unused implicit/password/refresh grants.
- Client authentication: **None** (public client). PKCE is required by the suite.
- Sign-in redirect URI: **`http://127.0.0.1:8765/callback`** exactly.
- Do not require a client secret or allow wildcard/remote callbacks.
- Assign only your own lab administrator temporarily for bootstrap, then the **`iam-lab-users`** group after group provisioning. Do not select broad Everyone access for routine exercises.

Save its **Client ID**. A client ID is configuration, not a secret. There is no client-secret value to copy into the repository. CLI logout revokes the locally stored access token where possible and removes local token files; it does **not** promise global Okta/browser SSO logout. Use Okta's own logout and a separate browser profile to switch participants.

## 3. Configure the default custom authorization server

Admin Console → **Security → API → Authorization Servers → default**:

1. Set audience to **`api://iam-lab`** in this dedicated test org. If your default server is already used by other integrations, create a separate custom server instead and set the suite issuer accordingly; do not alter their audience/policies.
2. Add a custom scope **`messages.send`**. Restrict it to this lab application through access policy; it is not an Okta management API scope.
3. Add claim **`groups`**, include in **Access Token**, value type **Groups**, filter **Matches regex** `^iam-lab-.*`. Include it for requests with `messages.send` (or always for the lab server). Avoid `.*`, which exports unrelated memberships.
4. Ensure user access tokens include the standard **`uid`** claim containing the Okta user's ID. The API requires it for containment/JIT. Confirm through a private Token Preview, not by posting decoded tokens publicly. The standard `sub` may be email-valued and is not the management user ID.
5. Create an **access policy** if missing; new free orgs may have no default policy. Assign it specifically to `IAM Lab PKCE`.
6. Add an allow rule for **Authorization Code**, only assigned users, and the requested scopes **openid**, **profile**, **messages.send**. Use the shortest supported access-token lifetime (for example five minutes). No refresh-token scope is requested.
7. Check policy/rule priority: another broad rule must not bypass your intended assignment/scopes. Requests with no matching policy should fail.

Issuer should be `https://YOUR_ORG/oauth2/default` (or your dedicated custom server ID). **Never** use the bare org issuer to protect your own API. Okta org-server access tokens are for Okta, not your resource server. API Access Management is available for free-plan testing but can require additional production licensing.

References: [groups claims](https://developer.okta.com/docs/guides/customize-tokens-groups-claim/-/main/), [access policy](https://developer.okta.com/docs/guides/configure-access-policy/-/main/), [PKCE flow](https://developer.okta.com/docs/guides/implement-grant-type/authcodepkce/main/).

## 4. Configure MFA without bypassing enrollment

Admin Console → **Security → Authenticators**:

- Enable a strong authenticator available to the free org, preferably phishing-resistant WebAuthn/FIDO2/passkey, or Okta Verify as supported by your device.
- Create an enrollment policy for the lab users requiring the chosen authenticator. Keep a recovery path and do not accidentally lock out your only administrator.
- Configure the lab application's **Authentication Policy / App sign-in policy** to require the appropriate factor assurance. Use the actual options in your tenant; Identity Engine menus/entitlements may differ.
- Verify that Alice/Bob/Eve cannot skip the required enrollment or sign-in challenge. Observe the System Log after real sign-in. Merely enabling an authenticator does not enforce it.

The suite uses Okta-hosted login: no password/MFA seed is stored locally and no factor is fabricated. It does not infer MFA from a valid JWT or treat `amr` as proof of a specific assurance unless you explicitly design that policy. Sign-in can reuse an existing Okta session according to your policy; force reauthentication in the tenant when demonstrating MFA.

## 5. Configure the local suite

```bash
cd okta-iam-suite
make setup
make configure
```

Edit ignored `config/local.json` with your actual org, custom issuer and Native Client ID. Keep audience `api://iam-lab` and API origin `http://127.0.0.1:8090`. Do not put a management token, client secret, password or message in JSON.

```bash
make doctor
make test
```

Doctor verifies issuer discovery and S256 support. It does not test MFA, assignments, group claims or authorization-policy outcomes. Use live login and the exercises for those.

## 6. Provision synthetic groups/users (optional management track)

Create an API token through **Security → API → Tokens** in the dedicated lab org using the minimum available administration rights for lab user/group operations and log reads. SSWS tokens inherit the creator's privileges and are not per-request scoped OAuth tokens; restrict token network access where available. Do not create a production Super Admin token for this exercise.

Store it locally without command-line/history exposure:

```bash
umask 077
mkdir -p .runtime
chmod 700 .runtime
read -rsp 'Okta lab API token: ' OKTA_TOKEN; printf '\n'
printf '%s' "$OKTA_TOKEN" > .runtime/okta_api_token
unset OKTA_TOKEN
chmod 600 .runtime/okta_api_token
make groups CONFIRM=lab-only
```

Assign the newly created **`iam-lab-users`** group to `IAM Lab PKCE` in the Admin Console. Review the assignment and any profile mappings. Then create three users with unique email aliases at a domain/inbox you control:

```bash
make join ACTOR=alice LOGIN=iam-lab-alice@YOUR_CONTROLLED_DOMAIN CONFIRM=lab-only
make join ACTOR=bob LOGIN=iam-lab-bob@YOUR_CONTROLLED_DOMAIN CONFIRM=lab-only
make join ACTOR=eve LOGIN=iam-lab-eve@YOUR_CONTROLLED_DOMAIN CONFIRM=lab-only
```

These create **STAGED** users (`activate=false`), no passwords or activation tokens in output. Activate them and complete credential/authenticator enrollment through the Admin Console's supported workflow. The free plan's email automation limitation means you must check the available activation experience rather than assume automated email delivery. Do not use your real administrator login as an actor or reuse a production identity. No management user grants imply Okta admin privileges.

If a create call succeeds but credential/ID registry persistence is interrupted, stop and inspect the lab objects privately. The automation refuses to adopt unregistered existing objects by name. Restore the matching private registry after confirming exact object IDs; do not disable the safety check. `.runtime/registry.json` is scoped to one org; never copy it to another org.

## 7. Validate live behavior

Follow [exercises.md](exercises.md), recording safe outcomes and inspecting audit records locally. Never publish callback URLs containing code/state, access tokens, actor emails, management IDs or raw System Log bodies.

When finished: leave/deactivate only registered synthetic actors with deliberate approval, revoke the SSWS token in Okta, remove the lab app assignment if no longer needed, and privately archive/remove local tokens. There is no automatic tenant-wide cleanup; group/app deletion is intentionally manual and reviewed.
